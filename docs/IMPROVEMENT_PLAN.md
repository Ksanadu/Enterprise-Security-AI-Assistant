## 1. 目标与当前基线

目标是将现有项目完善为：满足原设计场景、能够在本机与 Docker 中重复启动、可通过前端完整演示，并具备真实模型验证和后续运维基础的企业安全 AI Assistant 原型。

现有 React/TypeScript 前端、FastAPI 后端、RBAC、知识库、工单、看板、审计、测试和部署资产继续作为实施基础。默认离线模式保留，真实模型模式单独验收。

当前基线需要区分实现与验证：

- 默认路径为英文规则、TF-IDF 检索和 Mock 摘录式回答，不代表已验证真实大模型能力。
- 现有后端 JUnit 报告记录于 2026-09-15：1592 个用例，0 失败、7 跳过，即 1585 通过。这是历史结果。
- 完整 Docker 启动、真实 LLM/Embedding 回答质量与并发故障行为尚未完成本轮验收。
- 本机 `backend/.venv` 指向旧机器的 Python 安装，需要恢复。
- 本次审查发现了新的逻辑缺陷，因此旧状态文档中的“确认缺陷清单为空”不再作为交付依据。

本文件定义后续任务和完成条件，不表示任何缺陷已修复或任何验收已通过。各阶段状态必须由实际执行证据更新。

## 3. Phase 0：恢复本机环境并建立新基线

### 工作任务

1. 检查本机 Python、Node、包管理器、终端和 Docker 条件；记录可用版本及路径。
2. 按项目现有配置优先恢复 Python 3.12 环境。重新创建项目虚拟环境，避免复用指向旧机器的解释器。
3. 保留现有 `.env` 和运行数据，不在环境恢复中重置业务数据库、删除向量目录或覆盖密钥。
4. 安装 `backend/requirements.txt`、`backend/requirements-dev.txt` 和前端锁文件对应依赖。
5. 核查 `scripts/run-local.ps1`、`scripts/check.ps1` 等脚本，统一项目解释器入口，清除旧路径依赖。
6. 执行后端静态检查、类型检查和测试，以及前端类型检查、Lint、测试和构建。
7. 本机启动前后端，验证登录、提问、权限检索、工单和看板；建立新基线，明确通过、失败与跳过。

### 交付物与验收

- 可重复使用的本机项目环境及恢复说明。
- 新的检查记录；失败与环境问题分别归类。
- 前后端可以在本机交互，正常使用不再依赖旧用户目录。
- 环境恢复结束时不要求所有产品缺陷已修复，但必须能执行后续开发和验证。

## 4. Phase 1：修复风险、多轮对话与中文场景

### 工作任务

1. 将审查发现的风险误报、漏报先加入回归案例，再调整规则和对话处理。
2. 区分资产数量描述、正常操作、政策咨询与真实事件报告。不能仅因“4 台电脑”“打开文档”“在正式门户输入密码”就认定发生攻击。
3. 修复会话风险继承：保留事件峰值，但普通咨询和否定事实不能仅因 Low 信号被抬到历史高风险。
4. 修复历史消息查询，排除当前消息，避免重复拼接和丢失上一轮上下文。
5. 保存待确认事实和追问状态，正确解释“是的，我输入了”“Yes, I did”“只输入了验证码”等简短回答；存在歧义时继续追问。
6. 补齐钓鱼页面上提交 MFA/OTP/验证码的风险识别，区分正常验证与可疑页面泄露。
7. 建立中文及中英混合输入处理：覆盖意图、风险、否定、追问、提示注入和检索，不能只翻译界面。
8. 为中文离线演示提供可验证的检索方案，例如经审阅的双语知识内容与中文分词；真实语义向量效果在 Phase 5 单独验证。
9. 保持知识权限边界。普通员工的 VPN 演示使用员工可读指南，不为满足场景而放开 IT 内部 SOP。

### 必须覆盖的验收案例

| 类别 | 代表案例 | 验收要求 |
| --- | --- | --- |
| 原设计场景 | PRODUCT_SPEC.md §2 的 A/B/C/D 中文原句 | 意图、回答、授权来源和风险符合场景要求 |
| 高风险事件 | 打开可疑附件后出现异常弹窗 | High，产生 Security Ticket 并要求人工处理 |
| 正常操作 | `We have 4 computers in our office.` | 不因资产数量触发 Critical |
| 正常操作 | `I opened the approved document.` | 不因打开正常文档触发 High |
| 正常登录 | 在正式公司门户输入密码 | 不仅因输入密码判为凭据泄露 |
| 普通追问 | 高风险报告后询问密码要求 | 当前问题保持咨询风险，原事件仍被跟踪 |
| 多轮确认 | 点击可疑链接后回答“是的，我输入了密码/验证码” | 补全事实并升级原事件，不重复建单 |
| 否定与歧义 | “没有输入”“只打开了页面”“Yes, both” | 正确理解否定；歧义不能被当作确认安全 |

### 交付物与验收

- 风险与对话处理修复、中文场景支持、回归案例及事实状态说明。
- 原设计 A/B/C/D 场景和 §10 演示流程通过；中文版与英文版分别检查。
- 支持能力不能依赖特定演示句式；至少覆盖每个关键场景的改写和自然追问。

## 5. Phase 2：保证升级可靠、数据受保护、界面状态一致

### 工作任务

**升级与工单：**

- 高风险报告的记录与升级不能被生成模型、检索服务故障或知识库未就绪阻断。采用生成前的安全预判与事件持久化，最终结果继续遵守原管线的权限和结构化输出要求。
- 建立可持久化的升级任务、失败状态和重试入口，明确提交成功、等待处理、提交失败、人工已接手等状态。
- 使用幂等事件标识或等效机制，保证重复请求和重试不会重复建单；补充事实写入原事件。
- 修复工单编号分配与冲突处理，不依赖记录数推算唯一性。
- 缩短数据库写事务，避免在持有 SQLite 写锁时等待外部模型；明确回滚和失败审计边界。
- 区分系统自动标记 Escalated 与人工确认接手，不能把自动状态当作已经有人处理。

**数据保护与回答依据：**

- 修复短密码、纯字母密码、未加引号的多词口令及验证码脱敏遗漏；覆盖消息、标题、工单、备注和日志。
- 明确发送到外部 LLM/Embedding 的数据范围，实行必要的数据最小化；风险判断所需原始输入只在受控范围处理。
- 引用仅来自实际进入生成上下文的授权材料；区分检索命中、可生成答案和回答有依据，避免无条件标记 `grounded=True`。
- 修复 Embedding 缓存指纹，纳入模型、端点、维度及相关向量化配置。
- 复核历史消息、来源片段和角色变化后的访问边界。

**健康状态与前端：**

- 分离存活与业务就绪检查；知识库不可用、升级存储不可用等关键故障必须如实体现。
- 修复 Medium 已建单却显示“尚未提交工单”的文案和状态。
- 补齐工单分页与刷新，保证超过 50 条的工单可访问，新事件及时出现。
- 持久化用户手动建单与消息/事件的关联，避免重新登录后重复创建。

### 交付物与验收

- 明确的事件/升级状态模型、幂等和重试实现、数据保护修复、前后端一致性修复。
- 模型或知识库故障时，关键高风险报告仍被记录并进入可追踪的升级流程。
- 建单失败时，界面不得显示“已提交并将有人处理”；重试成功后只存在一个对应工单。
- 故障注入覆盖数据库写入失败、模型超时、重试、重复请求及并发消息；核查事务和审计结果。
- 失败记录、测试与截图使用模拟数据，不保存真实凭据或企业敏感材料。

## 6. Phase 3：Docker 全链路验收

### 工作任务

1. 准备支持当前 Compose 配置的容器环境，记录 Docker/Compose 版本及宿主平台。
2. 从干净检出和专用空测试卷构建启动，验证缺少 `.env` 时的默认启动路径，以及使用配置文件的启动路径。
3. 检查两套镜像、nginx、API、数据库、知识库、向量缓存及卷权限；健康检查必须反映业务就绪。
4. 在实际浏览器执行员工报告、风险升级、Security Team 查看与处理的完整流程，确认 CSP、代理和 UI 行为。
5. 验证重启、停止、重建、端口变更后的数据、会话和索引行为。
6. 演练错误配置、知识库加载失败、模型不可达、写入失败及容器退出，确认故障可解释。
7. 在具备容器条件的 CI 作业中加入构建、启动、就绪检查及 API 冒烟测试；浏览器全链路按发布门禁执行并保留记录。

### 交付物与验收

- 实际容器执行记录、自动化冒烟检查和故障处置说明。
- `docker compose up --build` 在干净环境可成功启动；浏览器完整演示通过。
- 重启后业务数据保留；知识库未就绪时不能被误判为业务可用。
- 不用 `compose config`、镜像布局模拟或 Dockerfile 检查替代实际启动验收。
- 测试卷与现有运行卷分离，清理仅针对明确的测试资源。

## 7. Phase 4：前端可视化 Demo

### 产品形态

在现有前端增加演示导览，用户仍通过真实后端完成业务交互。默认使用模拟知识、模拟账号和模拟事件。

| 场景 | 用户操作 | 可视化重点 |
| --- | --- | --- |
| 安全知识查询 | 提问并展开来源 | 回答、政策片段、引用和当前运行模式 |
| RBAC 对比 | 分别登录员工与安全团队账号 | 授权范围差异，禁止越权获取受限内容 |
| 钓鱼升级 | 报告可疑邮件并补充密码/验证码泄露事实 | 事实变化、风险变化、同一工单的升级 |
| 人工处理 | 安全团队打开队列、接手、备注、解决 | 新事件出现、处理状态与审计时间线 |
| 故障降级 | 使用受控演示环境触发模型故障 | 离线回答、升级待重试或明确失败状态 |

### 工作任务

- 增加示例问题、步骤导览、风险变化和事件时间线，兼容桌面展示与常见窄屏。
- 提供流程面板：意图识别 → 权限范围 → 检索 → 回答 → 风险评估 → 工单状态。展示实际结果，不能伪造模型调用或完成状态。
- 普通用户只看到使用所需信息；内部规则、检索调试、受限内容仅对获授权的演示账号开放。
- 保留离线模式，在无密钥情况下稳定运行；预留真实模型模式并明确标注当前模式。
- 通过独立账号或浏览器会话演示角色差异，不提供绕过后端身份验证的角色切换器。
- 提供演示数据初始化/重置工具，严格限制在演示环境和演示数据集，不影响生产或现有业务数据。
- 使用真实事件驱动刷新或合理轮询，避免展示旧工单和旧统计。
- 如提供录制回放，明确标注为回放，不能作为实时系统验收证据。

### 交付物与验收

- 前端可操作 Demo、演示脚本、模拟数据说明及模式说明。
- 离线模式下完整执行中文和英文核心流程；工单和看板结果来自后端。
- 真实模式入口在配置未就绪时清楚说明原因，不能默认为已连接。
- 错误、等待、失败和人工接手状态均可理解；演示素材不含密钥或真实敏感数据。

## 8. Phase 5：真实 LLM/Embedding 接入与验收

### 工作任务

1. 确认实际服务、模型、网络、密钥、费用预算和企业数据发送边界，密钥通过环境变量或秘密存储注入。
2. 先冻结离线基线，再依次验证以下组合，隔离生成与检索变化的影响。

| 组合 | 用途 |
| --- | --- |
| Mock + TF-IDF | 确定性离线回归与无密钥演示 |
| 真实 LLM + TF-IDF | 生成、模型分类、解析和故障处理验收 |
| 真实 LLM + 语义 Embedding | 语义检索与完整模型链路验收 |

3. 核查供应商接口兼容性、结构化解析、引用一致性、未知问题和提示注入处理。
4. 验证模型变更后的缓存失效与重新索引，分别校准语义和词法检索阈值。
5. 建立总体请求超时、重试和费用预算，协调 API、代理及前端等待行为；不只配置单次网络超时。
6. 覆盖服务超时、限流、空输出、错误输出、网络失败和 Embedding 不可用；验证高风险记录与升级不受影响。
7. 记录延迟分布、调用次数、Token/费用、降级比例及代表性回答，并安排人工审阅关键安全建议。

### 交付物与验收

- 三种组合的配置说明与验收记录，真实服务模型及版本信息。
- 真实模型下完成原设计演示；中文、高风险及权限案例均实际执行。
- 模型不能降低后端确定的高风险或决定访问权限；结构化异常有明确处理。
- 答案关键结论由授权来源支持，无法支持时明确说明不足。
- 未获得密钥、预算或网络条件时，该阶段保持未完成，不能以请求桩结果结项。

## 9. Phase 6：扩展质量评测与独立验收集

### 数据与覆盖设计

- 保留现有 40 题作为回归种子。建议扩展至至少 300 个单轮案例和 30 组多轮案例，并保证关键高风险与正常操作都有足够样本；数量只是覆盖投入，不能替代质量指标。
- 建立开发集与独立验收集；同一案例的近似改写不能分散到两套集合造成泄漏。
- 标注角色、语言、事实、意图、风险、允许来源、工单预期和理由，所有材料使用模拟数据。
- 覆盖中文/英文/混合输入、简短回答、否定、歧义、事实修正、话题变化、正常登录、正常文件操作和各类安全报告。
- 覆盖 RBAC、历史内容读取、提示注入、脱敏、上下文裁剪、模型异常、并发和重复请求。
- 标签依据 PRODUCT_SPEC.md 与经审阅的企业政策；先统一知识库、规则和评测预期中的冲突，再冻结验收集。

### 指标与门禁

| 指标 | 验收方法 |
| --- | --- |
| 意图识别 | 整体准确率及按类别、语言的混淆矩阵 |
| 风险识别 | 各级精确率/召回率，重点报告高风险漏报和正常操作误报 |
| 授权检索 | Expected-document Recall@K、越权返回次数、实际上下文范围 |
| 回答质量 | 引用支持率、关键结论正确性、无依据结论及建议操作安全性 |
| 升级可靠性 | 持久化成功、工单成功/待重试、最终送达和幂等结果 |
| 系统表现 | 请求延迟、错误、降级、并发和真实模型费用 |

原设计场景、冻结的关键高风险案例、RBAC 越权和升级丢失案例采用硬性门禁：必须全部符合预期。其他指标的具体阈值在基线测量后、验收执行前确定并冻结，不能根据最终结果下调。

### 交付物与验收

- 版本化评测数据、标签说明、独立验收结果与失败分析。
- 离线模式和真实模式分别报告；真实模型评测记录模型、配置、次数及波动。
- 失败案例转为回归案例；修复后保留新的独立验证，避免只证明记住了失败句式。
- 明确结论适用范围：测试集中的无漏报不代表真实环境永远无漏报。

## 10. Phase 7：正式运维能力与试点准备

### 工作任务

| 领域 | 必须补齐的能力 |
| --- | --- |
| 数据与迁移 | 引入迁移工具；验证现有数据升级、备份、恢复及保留/删除策略 |
| 升级与人工响应 | 对接通知渠道；记录送达、确认接手、超时提醒和重试结果 |

| 发布与运维 | 部署、升级、回滚、故障处置、备份恢复和责任分工手册 |

先完成单机试点必需能力，再根据负载推进扩容。SQLite 可继续用于原型；切换数据库不能被描述为只改一个 URL，必须验证驱动、迁移、事务与查询行为。

通知渠道接入后先在测试接收端演练，正式收件人和实际发送范围在部署时明确配置。

会话清理函数、保留天数等配置必须有实际执行入口和验证，不以“存在函数”认定定期清理已经完成。

### 交付物与验收

- 试点部署配置、监控和告警、备份恢复记录、升级回滚记录及运维手册。
- 完成一次备份恢复、一次发布回滚及一次高风险升级失败恢复演练。
- 服务重启后升级任务不丢失；多个 worker/实例不放大限流与锁定预算。
- 生产配置不能启用演示重置、演示账号或默认秘密；演示部署与试点部署分别说明。
- 达到试点条件不等于完成全部企业生产能力，交付记录必须明确规模与已知边界。
